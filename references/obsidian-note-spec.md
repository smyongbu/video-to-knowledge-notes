# Obsidian 图文知识笔记规范

执行视频知识笔记任务时，必须遵守本文件。

## 目录

1. 内容整理
2. 写作质量
3. 标题与课程结构
4. 配图判断
5. 950px 阅读规范
6. 图文关系与制作方式
7. 交付结构
8. 最终验收

10. FFmpeg 安全执行与防崩门槛

## 1. 内容整理

- 尽量保留课程原有的教学顺序和操作脉络，但不保留时间戳。
- 删除开场白、口头禅、关注引导、重复内容和无关过渡。
- 合并相邻的重复讲解，并把零散口语整理成连贯书面语。
- 只在不破坏课程顺序的前提下调整明显错位的内容。
- 不为了制作“完整知识体系”而加入大量课程之外的章节。
- 校正过度简化、不够严谨、可能过时或存在争议的表述。
- 适度补充理解主题必需、但视频未充分解释的背景知识。
- 不得编造事实；无法确认的内容必须明确标注。
- 对容易混淆的概念使用表格、案例或图表比较。
- 关键术语首次出现时，给出英文全称、中文名称、准确定义、解决的问题、工作原理和直观案例。

## 2. 写作质量

- 写成结构严密、通俗易懂、可独立阅读的知识教程，而不是视频摘要。
- 使用简体中文和专业自然的书面表达。
- 从基础到进阶逐层展开，每一章节解决一个明确问题。
- 默认读者完全没有相关基础。操作类内容按需要写清“要做什么、从哪里进入、点击或输入什么、画面会发生什么、这一步有什么作用、哪里容易误解”，不能假定读者已经认识界面或术语。
- 在保证零基础读者能跟做的前提下保留必要的技术细节。
- 避免空洞总结、碎片化列表以及用类比代替严格定义。
- 重要结论使用粗体；补充信息使用引用块；风险和误区使用醒目提示；操作流程使用有序列表；精确比较使用 Markdown 表格。
- 不在正文出现“视频中提到”“讲解者说”“某分某秒”等表述。

## 3. 标题与课程结构

- 笔记直接从正文教学内容开始，不创建“导读”章节。
- 不创建“课程目标”“学习目标”“本节目标”或意思相近的开场栏目，直接进入实际教学内容。
- 不创建“复习清单”“学习清单”“检查清单”“复习与自测”或自测题章节，也不在文末附带任务式勾选框。
- 不创建“官方参考资料”或单独的来源列表；必要核验链接就近放在相关内容旁。
- 文件名承担文档总标题的作用。正文不要再创建一个包住全文的单一 `# 文档总标题`；使用多个一级标题划分主要教学类别或阶段，二级标题表示类别内的功能、概念或步骤，必要时使用三级标题细分连续操作。避免层级跳跃、只有一个子项的空分类，以及全文只有一个一级标题、其余内容全被嵌套在其中的结构。
- 笔记文件名默认完整沿用源视频去掉扩展名后的名称，必须保留开头已有的课程编号、序号、数字、点号、空格和连接符。例如 `4. 认识界面-设计界面.mp4` 对应 `4. 认识界面-设计界面.md`。除非用户明确要求重命名，不得删除编号或另拟标题替换源文件名。
- 标题应描述实际教学内容，不使用“基础层”“能力层”等与课程无关的抽象包装。
- 课程先讲首页、再讲设置、再讲文件组织时，笔记也保持这一顺序；只对重复和口语进行整理。用标题把相邻内容归入清楚的类别，但不得为分类而打乱视频的教学顺序。

## 4. 配图判断

### 先判断画面类型

按视频顺序制作教程时，默认采用多图、高覆盖率的图文组织。凡正文描述视频中可见的对象、区域、位置、外观、按钮、菜单、图形、状态、变化、动作或结果，只要视频存在清晰对应画面，就应在相邻位置配图；纯抽象定义或视频没有可用画面的内容不机械添加装饰图。

先判断画面信息是否允许重绘：

1. **必须保留原画面的内容**：软件界面与操作步骤、实物外观、艺术或设计作品、地图、实验装置与现象、现场演示、摄影画面、游戏画面、精确数据图表，以及任何依赖位置、形状、颜色或细节才能学习的内容。使用视频原画面的局部截图，不重绘。
2. **默认必须重绘的内容**：抽象关系图、流程图、板书、手绘概念图、PPT 图解或信息卡片；若核心信息仅由文字、节点、箭头、线框、简单图标、颜色分组或层级构成，所有内容都清晰可辨、能够逐项核对，原始笔迹、粗糙排版、纹理与精确外观本身没有教学价值，并且重绘不会改变原意，则必须重绘为清晰的 PPT/矢量风格图解，不得仅因原截图尚可辨认就继续使用手绘截图。重绘后必须与原画面逐项比对。
3. **辅助视觉**：语义图标、步骤编号、箭头、高亮框或补充示意图能让内容更清晰时可以加入。辅助视觉必须明确是整理者添加的说明，不能冒充视频原内容，也不能替代真实操作画面或证据。
4. **无法确认的画面**：原图模糊、文字看不清、关系不确定时，不根据猜测重绘；改用清晰局部截图、寻找另一帧，或明确标注无法确认。

### 静态媒体决策硬门槛

制作媒体前，为每个静态候选建立一条内部决策记录，至少包含：编号、知识点、源时间或源帧、画面类型、媒体决策、决策理由、需要保留的原始细节或重绘核对项、成品路径和复核状态。画面类型只能从“必须保留原画面”“默认必须重绘的抽象图解”“辅助视觉”“无法确认”中选择；媒体决策只能从“截图”“重绘”“辅助新增”“舍弃”中选择。未分类、无理由或未复核的静态媒体不得进入成品。

同时满足以下条件时，必须选择“重绘”：

1. 教学信息能够完整枚举为文字、节点、箭头、线框、简单图标、颜色分组、层级或流程顺序。
2. 每个标签、数值、连接方向和层级关系都清楚可辨，能够逐项建立核对清单。
3. 原始手写笔迹、随手画的形状、粗糙对齐、画布纹理、光标和软件背景本身没有教学价值。
4. 不依赖照片、作品风格、精确坐标、数据曲线、公式排版、真实界面位置或其他必须保真的视觉细节。
5. 能够在不增加、删除、合并或改写信息的前提下完整还原。

图解出现在 Figma、FigJam、PPT、白板、画图软件或其他软件画布中，不等于它属于“必须保留的软件界面”。若当前知识点讲解的是图内概念关系，而不是如何创建、选择、拖拽或编辑该图，按图解内容本身分类；符合上述条件时仍必须重绘。只有当前步骤正在教学软件操作，或原始布局、笔迹、外观、精确数据与视觉细节本身具有教学价值时，才保留原画面局部截图，并逐图写明不可替代理由。

重绘优先使用 Mermaid、内联 SVG、外部 SVG 或确定性矢量／PPT 式制图方法；需要稳定显示时可以导出 PNG，但应保留可核对的矢量或结构化源稿。包含大量精确中文、术语和箭头时，不使用生成式图片模型代替确定性排版。

### 界面与实操课程的配图密度

界面、软件操作、实物演示等课程默认采用较高的视觉覆盖率，优先使用多张小而清晰的图片配合文字，不要为了减少图片数量而把多个知识点压进一张大图。

- 制图前先建立内部“可视描述—配图覆盖表”，逐个检查二级、三级标题以及每一段、每条列表中的入口位置、操作对象、界面区域、设置选项和可见结果。凡是读者需要“找到它”“认出它”或“看出变化”才能复现的内容，都应安排真实局部截图。
- 创建文件、打开入口、导入资源、展开菜单、切换面板等首次操作，只要视频里有清晰画面，就必须配入口截图。例如正文写“点击新建设计文件”时，应同时展示该入口，不得只写快捷键和文字说明。
- 一个具有可见过程的操作或需要听原讲解的知识点，默认直接从原视频剪成带原声 MP4。视频同时覆盖入口、关键过程和结果；只有静态界面、对象或状态才使用普通局部截图。禁止从无声预览或二次处理动画重新剪辑。
- 以完整讲解语句和画面动作共同决定视频起止点。在语句前后的自然停顿处剪切，不截断词句；每段只承载一个独立概念或连续操作，通常约 8～45 秒。知识点多时增加短视频数量，而不是合并成少数冗长视频。
- 每个 MP4 必须保留源片段的同步有效声音，默认采用 H.264、AAC、`yuv420p` 和 fast start。每段短视频必须以本段鼠标实际操作范围为裁剪主体和主要构图依据，禁止仅将源视频整帧缩小：先联合本段全部有效鼠标位置、点击或拖拽目标、鼠标操控区域所属的完整 UI、从按下到释放的路径、直接展开的活动 UI 和必须观察的直接结果，再用一块连续矩形裁剪窗口构图。固定区域采用稳定裁剪；跨区域操作按实际操作链拆成少量稳定镜头，或使用能完整容纳各操作区域 UI 的稳定构图，不逐帧追着鼠标移动。同一连续源画面内，相邻稳定镜头之间的裁剪中心或倍率变化默认使用短促、单向、缓入缓出的平滑运镜，不得把裁剪参数台阶式硬切。只有讲解完整界面空间关系，或鼠标实际操作范围确实覆盖完整界面的短暂片段可以保留全景。用户未指定时默认输出 1280×720；明确指定 480p、720p、1080p 或具体宽高时按用户要求。保持裁剪画面的自然比例和偶数尺寸，不无意义放大超过源视频有效分辨率。
- 鼠标、完整操作目标和关键动作必须全部在画面内，并且优先保证鼠标操控区域所属的整个 UI 功能单元完整。这里的“完整 UI”不是整个软件窗口，而是当前操作涉及的完整功能容器或相互关联的 UI 组合：菜单须保留触发入口、父菜单、子菜单、全部边界和当前项；弹窗、下拉列表、属性面板、工具栏或工具分组须保留当时可见的标题、外框、控件和必要关联内容；画布操作须保留完整被操作对象、有效路径、直接结果和必要定位上下文。任何正在使用的 UI 都不得只显示一半。
- 平滑运镜的起点、终点和所有中间帧都必须通过完整 UI 硬门槛。先为每个稳定镜头确定 16:9 安全裁剪框，再为过渡确定能够容纳活动 UI 联合边界的安全走廊；曲线使用无回弹、无越界的 ease-in-out（缓入缓出），常规约 0.4～0.8 秒，远距离跨区约 0.8～1.2 秒，完成后精确停住。目标靠近源画面边缘时锚定该边并随当前裁剪宽高推导位置，例如下方工具栏锁定底边、左上菜单锁定左边和上边；不得把起止 `x/y` 独立线性插值，因为中间帧可能反而裁断边缘 UI。两个特写无法直接安全衔接时，使用“当前特写 → 平滑拉远 → 短暂稳定全景 → 平滑推近 → 新特写”；全景只负责空间定位和承接界面状态变化，不承担长期细节教学。
- 同一连续源画面中的裁剪硬切默认判定为失败。只有原片本身已经切镜、前后画面没有可连续的空间关系，或逐帧验证证明不存在既可读又保持活动 UI 完整的平滑路径时，才允许在语义边界硬切，并在镜头计划中记录例外理由。平滑运镜只改变单块连续矩形取景，不使用交叉溶解、帧混合、光流补帧、重复帧、运动模糊或变速；原片发生菜单关闭、面板打开等界面状态切换时，让裁剪框保持稳定，使变化读作原操作而不是镜头跳变。
- 鼠标没有操作到且与当前步骤关系较弱的工具栏、属性栏、画布、空白区和其他面板应尽量少纳入画面，但这只是构图优化，不是必须删除的硬条件。为了完整呈现鼠标操控区域的整个 UI、保留定位关系、补足 16:9 或维持稳定镜头，可以保留必要的相邻未操作区域；完整 UI 的优先级高于缩小无关区域。裁剪只允许使用连续矩形窗口改变取景，不得用遮罩、涂抹、黑块、挖空、拼贴、局部删除或中性边带去除未操作区域。一个镜头无法清楚容纳多个完整 UI 时，在语义边界拆成多个稳定镜头。
- 不为剪辑后的 MP4 新增、烧录、叠加或生成字幕，也不默认交付旁挂字幕文件。源视频已经存在的硬字幕可随有效画面自然保留或在裁剪时被裁掉，但不得拼接字幕条、扩展画布或牺牲有效操作区域只为保留硬字幕。
- 把人工校正后的转写文字紧接在每个有语音的 MP4 下方，覆盖该片段的概念、操作和结果；不写时间戳，不堆成逐句字幕格式，不让视频下方为空。
- 讲解者点名可见菜单项、模板、按钮或图标时，即使没有点击，也要为每个对象配置紧裁小图，或用一张能将所有对象直接读清的紧凑局部图；不得只留纯文字枚举。
- 介绍包含三个或更多区域的完整界面时，优先把左侧栏、画布、工具栏、右侧栏拆成多张局部图逐一说明。全景图可以作为辅助地图，但不能让多个需要阅读的区域在全景中缩得过小。
- 纯文字表格可以整理名称和作用，但不能作为界面结构的唯一说明。若表格中的每一行对应一个可见区域、按钮或面板，应在表格后按区域加入小截图，或改写成“短说明＋局部截图”的重复图文单元。

### 可视描述—配图覆盖审查

- 把正文中可以由画面证明或说明的句子视为“可视描述”。可视描述包括界面结构、按钮位置、菜单层级、选项名称、图形外观、对象关系、操作动作、前后状态和结果变化，不只包括软件 UI。
- 每条可视描述都必须映射到一张或多张紧邻图片。若同一段或列表列出四个区域、四个选项或四种状态，就让四项分别有小截图，或使用一张在最终显示宽度下能把四项全部直接看清的紧凑截图；只显示其中一项不能算完成覆盖。
- 当文字与图片无法一一对应时，优先把长段落或长列表拆成多个“名称或步骤＋简短说明＋局部截图＋图注”的图文单元，而不是在段末补一张泛化全景图。
- 同一图片可以覆盖相邻多句话，但前提是每个被描述对象都在图中清楚可见、可定位、可读，并且图注说明它对应哪些内容。不能用一张只显示菜单的图代替整段界面结构说明。
- 完稿后反向审查：从每段文字查对应图片，再从每张图片查它服务的文字。任何有清晰视频画面却只有文字的可视描述都必须补图或改写。

### 截图规则

- 不得按固定间隔、逐镜头或连续帧批量截图，也不得用整帧截图代替知识整理。
- 截图保留当前知识点的“最小充分上下文”。例如讲解一个菜单时，要保留菜单、触发按钮及足以确认其所在位置的一两个相邻锚点；不要只剩一个无法定位的孤立按钮，也不要保留完整侧栏、整块画布或整页无关内容。
- “最小充分上下文”不等于保留整块画布或完整侧栏。若真正有用的内容只在右侧中部、某个菜单或弹窗中，就围绕该目标紧密裁剪，只额外保留触发入口或少量定位环境。
- 先框出相邻文字真正讲解的最小教学目标，再从目标边界向外只保留约 8～24px 或不超过截图短边 10% 的边距。只有触发入口、父级菜单、面板标题等确实帮助定位的内容才可进入边距之外。
- 每张截图在选帧后和最终渲染后都必须单独审查构图。目标本身原则上应占图像宽度和高度各至少 60%，目标与必要定位上下文合计至少 90%，无关空白、背景、未讲解区域或重复列表不超过 10%；只有空间关系本身是当前教学内容时才可例外。
- 每张截图必须有一个明确的主教学目标，即相邻文字要求读者观察的按钮、菜单、面板、数值或结果。读者第一眼应直接落在目标上，而不是在图中搜索。关键界面文字应达到约 14～16px 或具有同等直接可读性；达不到时必须继续紧裁、拆图或增强。
- 若“说明它在哪里”和“看清它是什么”无法由一张紧凑截图同时完成，就输出两张图：先用定位图说明目标处于界面的哪个区域，再用细节图紧裁按钮、菜单、面板或条目。不得为了保留定位关系而让细节图中的目标变小。
- 不以源图分辨率或成图尺寸判断清晰度。图片在 950px 正文中显示后，重要按钮、菜单文字和数值必须直接可辨；若它们因全景缩放而变小，就改用更紧的局部图，而不是继续放大整张图片。
- 不得把低分辨率裁剪图直接插值放大后当作“高清图”使用。单独打开最终栅格图片文件并以 100% 原始像素比例检查；这里的 100% 是 1 个图片像素对应 1 个屏幕 CSS 像素，必须关闭适应窗口、自动缩放和插值预览，图片超出屏幕时按原比例滚动或分块覆盖整张图。只要文字边缘发虚、图标轮廓成块、压缩噪声明显，或仅有轻微模糊，就必须执行“重新取帧—紧密裁剪或拆图—必要时 AI 高清化—原帧核对—最终复检”的清晰度修复流程。PNG、JPG/JPEG、WebP 等逐张检查；动图逐帧或至少覆盖全部不同画面状态。SVG 等矢量图片不执行栅格 100% 或 AI 高清化，改为在最终自然显示尺寸和 2 倍渲染尺寸逐项检查文字、线条、图标、颜色与边界。
- 是否进入清晰度修复只由当前图片文件本身在 100% 原始像素比例下是否清楚决定，不参考 Obsidian、浏览器缩放、Markdown 显示宽度或嵌入后的视觉效果，也不设放大倍率、源图尺寸、成图尺寸、显示宽度、DPI 或像素密度门槛。先换用更清楚的相邻原帧，再重裁或拆图；若当前最终候选仍出现轻微发虚、粘连、断笔、块化、锯齿或压缩噪声，就必须尝试保真 AI 高清化。若换帧、重裁或拆图后已完全清楚，则不机械运行 AI。含文字的软件 UI、数据图表、地图或其他精确证据画面优先使用不做语义重绘的保真超分模型；提示式图像生成或扩散模型只能生成候选，必须逐字逐数、逐图标、逐边界和逐位置核对，发现任何改写或位移就拒收。
- 重新取帧时，优先从原始视频直接解码帧，不截播放器窗口；检查目标前后相邻帧，选择静止、对焦清楚、压缩伪影较少且没有鼠标遮挡的一帧。若有更高分辨率原视频或原始课件，优先换用更高质量来源。
- 重新取帧并紧裁后若当前最终候选仍存在轻微模糊，必须尝试保真 AI 超分辨率或高清化，也可配合克制的去噪、保边放大、局部对比度和锐度优化。这里的 AI 只负责恢复可读性，不得进行语义重绘、生成修补或想象性补全。
- 增强前后必须在两者各自 100% 原始像素比例、等尺寸比较视图和放大视图中并排核对，并使用 50% 半透明叠加检查对齐，逐项检查文字笔画、按钮名称、数字、图标轮廓、颜色、边界和空间位置。禁止使用会补写或改写这些细节的结果；不得把推测生成的内容冒充原画面。
- 对界面文字做人工目视检查；可辅以 OCR 比对，但不得仅凭 OCR 成功就判定清晰。若出现伪文字、新增笔画、涂抹、光晕、边界移动或颜色改变，立即弃用增强图并改用其他源帧或更保守的处理。若仍无法可靠辨认，该图不得进入成品；若它不可替代且删除会造成可视描述缺图，不得宣称任务完成，应明确报告阻塞并请求更清晰源素材，不猜测或生成原图内容。
- 不制作“只有一小块有用、其余大面积空白”的纵向或横向长图。版本历史、长列表等界面只截与当前步骤相关的条目、菜单和少量相邻内容。
- 天然很窄或很长的侧栏、版本列表和菜单，在原始宽度已经可读时允许按自然宽度显示，不得为了占满 950px 正文而横向拉伸；是否高清化仍只看图片文件本身在 100% 原始像素比例下是否清楚。
- 若有用信息集中在左上角、右侧中部或其他小区域，围绕该区域重新裁剪，并仅保留能确认位置的少量相邻内容；不得因为原画面是竖图、全屏或长列表就保留原比例。
- 讲解版本历史时，只截面板标题、当前版本和正在说明的版本条目；裁掉旁边的大画布、面板下方空区和无关历史条目。讲解左上角 Main menu 入口时，只截 Figma 图标、提示名称及一两个定位锚点；裁掉 Pages、Layers、完整侧栏和空画布。其他单一入口、按钮或面板按同一标准处理。
- 同一知识点需要多个视角时，优先分别输出多张小图并逐张说明。只有每个子图在最终宽度下仍清楚时，才可合并为对比图；不得把可读性牺牲给拼图数量。
- 若保留完整界面总览，必须用 3～5 个清楚的编号、高亮或标签与正文说明对应；总览只负责空间定位，仍要另配需要阅读的侧栏、按钮和菜单特写。
- 局部截图必须服务于明确的知识点，只保留必要区域，并裁掉字幕、水印、头像、播放器控件、讲解者画面和无关背景。截图应注明其性质，不得标成原创图。
- 不因画面仅仅被称为“图表或 PPT”就跳过分类而自动重绘；必须先执行“静态媒体决策硬门槛”。满足默认强制重绘条件的板书、手绘关系图、简单流程图或 PPT 图解不得继续使用原始截图；只有版式、原始外观、精确数据、公式、坐标、标注或视觉细节本身具有教学价值时才使用原画面局部截图，并记录不可替代理由。
- 重绘必须保持原内容的事实、数据、节点、标签、箭头、层级和逻辑关系。可改善清晰度与排版，但不能省略细节、合并含义或改变原结论。
- 一张图只表达一个主要问题。可以根据理解需要加入新的知识地图、架构图、流程图、图标或信息卡片，但它们只能作为补充说明，不能替代需要保真的视频画面。
- 精确比较优先使用 Markdown 表格。

### 信息密度

图中只保留核心概念、关键关系、流程方向、必要分类和少量辅助说明。不要放入完整段落、大量定义、正文已解释的内容、无关修饰或装饰标签。

出现以下任一情况时拆图或重构：节点超过 8～10 个；一个节点超过两行文字；连线大量交叉；同时表达流程、层级、对比和案例；一张截图同时要求阅读三个或更多界面区域；必须缩小文字才能容纳；缩放到 900px 后不能一眼看清结构。

### 视觉质量

- 明确图表主题与阅读方向，区分重点和次要信息。
- 使用支持简体中文的字体，避免乱码、伪文字和错字。
- 对齐整齐、留白适中、配色克制统一，保持简洁、现代、专业。
- 不使用无意义机器人、人物、光效或平台装饰。
- 原创重绘图不保留字幕、水印、头像、平台标志或视频模板装饰；允许使用的局部截图也应尽量裁除这些无关元素。
- 不为了美观牺牲准确性。

## 5. 950px 阅读规范

最终阅读环境：Obsidian 正文宽度 950px、浏览缩放 100%、不点击图片放大。

### 真实渲染验收

必须在 Obsidian 阅读视图，或能够实际解析最终 Markdown 的像素等效预览中检查整篇笔记的排版、媒体引用和可用性，不得只查看 Markdown 源码。固定正文宽度 950px、缩放 100%，从头到尾检查标题、正文、表格、图片、图注和链接。此处不判断图片是否需要 AI 高清化；高清化只由图片文件本身的 100% 原始像素检查触发。

默认选择后台像素等效预览，并通过直接读取最终 Markdown、附件、引用和哈希完成文件审计。不得为了例行验收而启动、切换、聚焦或控制用户的 Obsidian，也不得向其发送鼠标或键盘输入。只有用户明确要求真实 Obsidian 验收，或已发现只能在 Obsidian 内复现的具体显示问题且用户明确同意控制软件时，才允许操作 Obsidian；检测到用户正在使用该窗口时立即停止自动操作，改用后台证据，不抢占窗口。

出现以下任一情况时必须修改并重新渲染：重要界面文字需要放大；全景图使侧栏或按钮缩小；表格过窄或列宽失衡；图片周围有异常空白；原始 HTML、CSS、代码标签或编辑残片暴露；元素溢出正文宽度；图片与说明错位。

截图若经过增强，必须另外在图片文件各自 100% 原始像素比例、等尺寸比较、200% 放大比较和 50% 半透明叠加视图中与未处理原帧对照：确认按钮名称、文字笔画、图标、颜色、边界和空间位置没有被改变。出现模糊、过度锐化光晕、涂抹感、伪文字或新增细节时，处理结果不得使用。

### 图片画布与自然显示

成品 Markdown 不写图片宽度属性，图片会按文件自身画布和阅读区域自然显示。因此必须在保存附件时把画布裁到目标周围，并把自然显示宽度控制在适合阅读的范围。下表是 950px 正文中的默认通过区间：

| 图表类型 | 默认自然显示宽度验收区间 |
|---|---:|
| 全局知识地图 | 850～920px |
| 系统架构图 | 780～900px |
| 普通流程图 | 650～820px |
| 概念关系图 | 550～760px |
| 单个概念卡片 | 320～520px |
| 竖向步骤图 | 420～650px |
| 简单示意图 | 300～500px |
| 单个按钮、菜单或弹窗 | 280～520px |
| 单个侧栏或工具栏局部 | 360～650px |
| 两个状态的局部对比 | 600～850px |
| 完整界面定位图 | 760～900px，仅用于整体定位 |

不要在 Markdown 中写 `width`、`height`、`style` 或 `align`。截图的自然显示大小应由“有用内容的尺寸”决定，而不是由原始视频画幅决定；窄菜单、按钮和弹窗应裁成小画布并输出足够清晰的像素尺寸，不要把它们留在 16:9 全画面里再整体缩小。

对每张最终图片同时记录文件像素宽高 `P_w × P_h` 与 950px 阅读视图中的实际自然显示宽高 `R_w × R_h`。栅格图再计算横向像素密度 `D = P_w / R_w`。按以下硬规则判定尺寸，不得只凭“看起来差不多”通过：

1. `R_w` 超过 950px、产生横向滚动、溢出正文或被裁切，直接判定过大并修复。
2. `D < 1` 表示阅读视图正在放大栅格图，直接判定像素尺寸过小；换用更高分辨率原帧或重新渲染，不得靠插值冒充清晰度。
3. `D > 2.1` 默认判定文件像素尺寸过大，应在不损伤文字和细线的前提下高质量缩小到约 1～2 倍显示密度；只有读者确实需要点开查看精密地图、数据或长图细节时才允许保留，并在逐图审核记录中写明理由。
4. `R_h > 950px` 的单张截图默认判定过高，应裁紧或拆图；只有连续长结构本身就是教学对象、拆分会破坏关系且所有重要文字仍直接可读时才允许例外，并记录理由。
5. 自然显示宽度超出上表对应区间时默认不通过；只有空间关系、连续长结构或天然窄小目标确实需要例外，并且重要文字不低于约 14～16px、目标占比与无关区域指标全部通过时，才可在逐图记录中说明理由后通过。天然很小但本身已直接可读的按钮、菜单和提示不得为了进入区间而拉伸。
6. 即使宽高与密度在区间内，只要主目标占宽度或高度不足约 60%、目标与必要上下文不足约 90%、无关区域超过约 10%，或关键文字低于约 14～16px，仍判定为构图过大或内容过小，必须重裁、拆图或换帧。

这里的“过大／过小”指文件画布、自然显示尺寸、像素密度与教学信息量是否匹配，不以文件字节数或 DPI 单独判断。所有例外都必须是逐图、可复核的例外，不能用一个总说明批量放行。

### 表格

- 两列教学表在 950px 正文中的最终宽度通常控制在 600～820px，并保持居中或与正文主轴对齐；第一列约占 20%～35%，第二列用于解释。
- 若 Markdown 默认表格明显过窄、列宽失衡或留出大块空白，应改用普通列表、定义式说明，或拆成多个图文块；不要改用 HTML 表格。
- 当表格行表示可以在画面中找到的界面区域、按钮或面板时，表格只能负责名称和作用的比较，不能替代真实局部截图。优先在表格后加入对应小图，或直接改写为“名称＋简短说明＋局部截图”。

### 构图比例

- 普通知识图优先 4:3、3:2 或接近方形。
- 系统架构图优先 4:3 或 5:4。
- 环形结构使用接近方形；层级结构和步骤图可以使用竖图。
- 对比图可使用双栏 3:2 或 4:3。
- 只有节点较少时才使用宽幅演进路线。
- 不默认使用 16:9，不制作不必要的超宽扁图。
- 软件截图不必强行套用固定比例，应围绕有效信息紧密裁剪。只有在讲解空间位置关系时才保留较宽上下文。

横向节点超过 4～5 个、标签需要缩小、左右距离过远或存在大量空白时，改成两行折返、纵向、环形、分层结构，或者拆成总览图与局部详图。

### 图中文字

按图片最终显示尺寸计算字号。当图片最终显示宽度为 760～900px 时：

| 文本层级 | 最终显示字号 |
|---|---:|
| 主标题 | 26～32px |
| 一级节点标题 | 20～24px |
| 普通节点文字 | 18～21px |
| 次要说明 | 不低于 16px |
| 图注、轴标签和补充文字 | 不低于 15～16px |

若重要文字在最终显示尺寸下小于约 16px，重新设计。不要通过缩小字号解决空间不足；应增高画布、换行、改为纵向或拆图。节点标题尽量控制在 2～8 个汉字，解释放回正文。

## 6. 图文关系与制作方式

图片必须放在对应操作或知识点附近。需要保真的画面使用原始局部截图；满足“静态媒体决策硬门槛”且能无损还原的抽象图解默认必须重绘；图标和辅助示意图可在确实提升理解时加入。不要仅因为正文能说明就排除图片，也不要让辅助图取代真实操作或原始视觉信息。

### 普通图片的 Markdown 格式

成品笔记中的视频截图、PNG、JPG 以及作为独立文件保存的 SVG，只使用下面这种标准 Markdown 形式：

```markdown
![Main menu 主菜单入口](attachments/Figma界面/Main-menu主菜单入口.png)

图：左上角 Figma 图标是 Main menu 的入口。
```

- 图片语法单独占一行，图注另起一行使用普通正体文字。禁止使用 `*图：……*`、`_图：……_` 等斜体图注，以及任何会让文字倾斜或变形的样式。
- 只使用相对路径和语义明确的文件名；不使用绝对路径、Base64、Data URI 或网络临时地址。
- 不使用 `<div>`、`<img>`、`<picture>`、`style`、`width`、`height`、`align`、HTML 表格或 CSS 包裹普通截图和独立图片。
- 不为并排、居中、缩放、边框或阴影插入 HTML/CSS。需要控制大小时，直接紧裁并调整附件本身的画布和像素尺寸；需要比较时，按顺序放置两张图片并分别说明。
- Mermaid 代码块和内联 SVG 若本身用于表达流程、关系、层级、结构或可编辑知识图表，可以直接保留在笔记中，不必先转成图片。必要的少量 HTML/CSS 图表也可以保留，但不得用这些代码包装普通截图、设置普通图片尺寸或进行装饰性排版。

### Obsidian 视频嵌入格式

带原声短视频使用 Obsidian 内嵌语法并单独占一行：

```markdown
![[attachments/Figma界面/拖动对象并吸附.mp4]]

视频：拖动对象时观察吸附提示，并听取操作条件的讲解。
```

- 使用相对库路径和语义化中文文件名，不使用绝对路径、网络临时地址或 HTML `video` 标签。
- 视频说明另起一行，指出应观察和聆听的重点。
- 不在嵌入语法中写尺寸；通过剪辑文件本身的分辨率和紧裁范围适配 950px 阅读宽度。
- 视频应允许读者主动播放、暂停和拖动进度，不要求自动播放或循环。
- 不为成品 MP4 新增字幕流、烧录字幕或旁挂字幕；用户明确要求字幕文件时才另行制作。源视频已有硬字幕可随有效画面自然保留。

### 图文最小单元

操作类内容按下面的顺序组织：

1. 用一句简短文字说明一个目标、动作或本步要观察的变化；不要让一句话同时承载多个连续动作。
2. 紧接一张只展示该目标的局部截图。
3. 用图注指出截图中的关键位置、动作或结果，不机械重复小标题。

不要让一张图与对应解释相隔多个段落，也不要连续堆放多张没有过渡说明的图片。一个纯文字表格若描述的是可见界面，应保留表格的精确比较作用，同时在相邻位置加入对应局部图；必要时改为多个“区域名称＋作用说明＋小截图”的图文块。

一段文字或一组列表只在所有可视描述都能从相邻图片中直接找到时才算图文完整。若列表包含多个界面区域、开关、菜单项、图形或状态，而现有图片只能清楚显示其中一部分，就把列表拆开并分别配图；不得用“一张大概相关的图”代替逐项覆盖。

若同一操作存在入口、操作过程、结果状态或重要口头讲解，默认用一段紧裁的带原声 MP4 连贯呈现，并把校正后的讲解文字紧接在视频下方。视频从完整语句前的自然停顿进入，在结果和讲解结束后的自然停顿退出，避免冗长等待、重复操作和无关知识点。每个独立知识点都可以配置自己的短视频；只有某个静态细节必须单独放大才能读清时，才额外补充局部截图。

包含中文、术语、箭头和结构关系的图表，优先选择 Mermaid 代码块、内联 SVG、外部制作的 SVG/PNG，或其他确定性矢量／PPT 式制图方法。需要继续编辑、搜索或复用节点关系时，优先保留 Mermaid 或 SVG 源码；源码必须简洁、能在 Obsidian 中正确渲染，并逐项核对文字、箭头、节点和层级。只有需要视觉表现力且不包含大量精确文字时才使用 AI 图片生成。不得用 Mermaid、SVG 或 HTML/CSS 代码包装视频截图或冒充真实界面。

AI 生成图片若出现中文乱码、伪文字、错字、术语错误、箭头错误、重复节点、结构错误、字体过小或构图过宽，必须重做。

## 7. 交付结构

```text
视频所在目录/
├── 原视频.mp4
├── 主题名称.md
└── attachments/
    └── 主题名称/
        ├── 团队权限关系.svg
        └── 首页侧栏局部.png
```

- 默认把 Markdown 笔记直接放在源视频所在目录，与视频处于同一层级。不得默认再创建一个主题文件夹把笔记藏在下一层。
- 配图放在视频同目录下的 `attachments/<主题名称>/` 中，笔记使用 `attachments/<主题名称>/图片名.png` 等相对路径。多个视频或多篇笔记共用同一视频目录时，每篇笔记使用独立附件子目录。
- 临时抽帧、转写和渲染文件可以放在工作区，但不得把工作区路径当作最终交付位置。除非用户明确指定其他目录，最终笔记必须写回源视频目录。
- 不移动、不重命名、不覆盖源视频；不覆盖与本次任务无关的同名文件。若笔记文件已存在，应在确认是本任务旧版本后再原位更新，否则使用不冲突的语义化名称。
- 写入后重新枚举源视频目录，确认视频与 Markdown 同层、引用的附件全部存在。网络共享目录必须通过新的独立读取验证，不能只相信复制命令返回成功。
- 文件名必须表达内容，不使用 `001.svg` 等无意义名称。
- 图片使用相对路径和最简单的 `![说明](相对路径)` 语法；不在 Markdown 中写尺寸、对齐或样式代码。
- 中文文件名、中文路径和文件内容使用 UTF-8，确保不乱码。
- 图注应解释图的用途或结论，不机械重复标题。

## 8. 最终验收

### 最终图片审核门槛

必须在全部图片资产写入最终附件目录之后执行，并审核最终目录中的实际文件，不能用候选目录、缓存、工作区副本或早期版本代替。分别枚举 Markdown 的全部图片引用与附件目录中的全部图片资产，引用缺失和无引用残留都必须为 0。审核范围包括 PNG、JPG/JPEG、WebP、GIF、独立 SVG 及实际使用的其他图片格式；栅格图按 100% 原始像素规则检查，动图逐帧或至少覆盖全部不同画面状态，矢量图按最终自然显示尺寸和 2 倍渲染尺寸检查。审核仅作为任务内部过程：在临时工作目录维护逐图结构化记录，至少包含相对路径、格式、画面类型、媒体决策、决策理由、保留原截图的不可替代理由（如适用）、最终文件 SHA-256、实际像素宽高或 SVG 视口、950px 阅读视图自然显示宽高、默认尺寸区间及例外理由、清晰度检查结果、构图判定、修复轮次、AI 尝试与接受／拒绝原因、Markdown 引用次数和最终状态；不得在笔记目录、附件目录或源视频目录生成或交付审核 JSON、审核 Markdown、表格、清单或其他审核文件。

尺寸与清晰度分开处理：按“图片画布与自然显示”中的硬规则判断图片是否过大、过小、过窄、过扁、目标偏角、空白过多或在 950px 阅读视图中不能直接读清；不通过时重新裁剪、拆图或调整输出画布，不用 Markdown 尺寸参数掩盖问题。当前最终候选在 100% 原始像素比例下只要有一点模糊，就启动清晰度修复：先检查相邻原帧并换取最清楚的一帧，再重裁或拆图；若当前候选仍有轻微模糊，必须尝试保真 AI 高清化。换帧、重裁或拆图后已经完全清楚时不机械运行 AI。AI 处理不得改变最终分辨率，除非用户明确要求；任何改字、伪文字、补笔、缺笔、图标变形、颜色改变、边界或位置移动、涂抹、光晕和过度锐化都必须拒收。

每次修复或覆盖后，都要重新读取最终附件目录中的实际图片，更新逐图记录中的 SHA-256 并重复审核。只有最终图片已全部审核、未审核数为 0、待修复数为 0、失败数为 0，且 Markdown 引用的全部图片都存在时，才允许交付。最终答复报告审核总数、换帧／重裁／拆图数量、AI 尝试数、AI 接受数、AI 拒绝数和最终通过数，不附加审核文件。

逐张检查：

1. 图片在 950px 行宽中是否过宽或过扁？
2. 是否为了容纳节点缩小文字？
3. 所有重要文字是否无需放大即可看清？
4. 次要文字是否仍达到正常可读字号？
5. 横向节点是否过多，是否应换成两行、竖向或拆图？
6. 图片是否存在过多空白，宽度是否匹配信息量？目标本身是否原则上占宽度和高度各至少约 60%，目标与必要上下文是否达到约 90%，无关区域是否控制在约 10% 以内？
7. 小图是否不必要地占满整行？
8. 正文是否重复图片已经表达清楚的内容？
9. 图片是否放在最有助于理解的位置？
10. 中文、英文术语、数据和箭头关系是否正确？
11. 这张图是否明显提升了理解、记忆、视觉定位或操作复现？
12. 是否把任何需要保留原画面的内容错误地重绘了，而不只是软件 UI？
13. 是否把满足默认强制重绘条件的板书、手绘关系图、简单流程图或 PPT 图解错误保留为原始截图？保留截图时是否逐图记录了不可替代理由？重绘图是否逐项保留了原图的节点、标签、箭头、数值、层级和结论？
14. 截图是否既裁掉无关区域，又保留了足以定位和复现操作的上下文？
15. 辅助图标、箭头和高亮是否没有遮挡、篡改或替代原始信息？
16. 没看过视频的读者能否凭笔记完成相同学习过程？
17. 创建文件、打开入口、菜单选择和结果变化等可视步骤，是否仍有只有文字而没有截图的段落？正文中所有界面区域、按钮、菜单、图形、对象、状态与变化等可视描述是否都已逐条映射到相邻图片？
18. 全景图是否承担了细节教学，导致侧栏、按钮或文字在正文中变小？若是，是否已经按区域拆成多张小图？
19. 每张截图是否都经过单独裁剪审查？是否先框定最小教学目标并只向外保留约 8～24px 或不超过短边 10% 的必要边距；目标本身是否原则上占宽度和高度各至少约 60%，目标与必要上下文是否至少约 90%，无关区域是否不超过约 10%；若有用信息只在角落或中部，是否已经围绕它重新裁剪？
20. 是否用纯文字表格代替了本应出现的界面局部图？
21. 每张图前是否有观察说明，图后是否有解释关键位置或结果的图注？
22. 合成长图或对比图后，每个子图是否仍无需放大即可阅读？若否，是否已经拆开？
23. 是否在实际解析最终 Markdown 的 950px 阅读视图中检查了整篇笔记，而不只是查看图片源文件？
24. 关键界面文字是否达到约 14～16px 或具有同等直接可读性；菜单、弹窗、按钮或侧栏特写中的主要对象是否原则上占画面宽度和高度各至少约 60%？
25. 两列表格是否达到合适宽度和列宽比例；若表格对应可见界面，是否已经配上局部截图？
26. 是否已单独打开每张最终栅格图片，以 1 个图片像素对应 1 个屏幕 CSS 像素的 100% 比例逐张目视检查，关闭适应窗口、自动缩放和插值预览，并在大图超出屏幕时滚动或分块覆盖整张图；是否没有使用 Obsidian 显示效果、源图尺寸、成图尺寸、DPI 或像素密度决定是否高清化？SVG 等矢量图是否已在最终自然显示尺寸和 2 倍渲染尺寸检查？
27. 当前最终候选在换帧、紧裁或拆图后若仍出现哪怕轻微模糊、粘连、断笔、块化、锯齿或压缩噪声，是否都已执行“AI 高清化—原帧复检”；换帧、重裁或拆图后已完全清楚时，是否避免了无意义的机械增强？
28. 经过 AI 高清化或其他增强的截图是否在各自 100% 原始像素比例、等尺寸比较、200% 放大比较和 50% 半透明叠加视图中与相邻原帧逐项核对，确认文字、数字、图标、颜色、边界和位置没有变化，也没有伪文字、新增或缺失笔画、过度锐化、光晕、涂抹或新增细节？
29. 每一段和每一条列表是否完成了“文字查图、图片查文字”的双向覆盖审查？描述多个可见对象时，是否每一项都能在图片中直接找到？
30. 标题是否把内容分成清楚的教学类别并保持视频原有顺序；完全没有相关基础的读者是否能仅凭笔记理解入口、动作、结果和作用？
31. Markdown 源文件中的普通截图和独立图片是否全部只使用 `![说明](相对路径)`；是否完全没有用于普通图片布局的 `<div>`、`<img>`、尺寸属性、HTML/CSS 或 Base64？保留的 Mermaid、内联 SVG 或少量 HTML/CSS 是否确实属于知识图表，而不是图片包装代码？
32. 读者能否第一眼看到每张截图的主目标？若仍需在完整侧栏、画布、长列表或大片空区中寻找目标，是否已继续紧裁，或拆成定位图与细节图？
33. 版本历史、Main menu 等单一目标截图是否只保留当前讲解的面板、条目、图标和少量锚点，而没有把完整画布、完整侧栏或面板空区一起截入？
34. 是否错误地使用单个 `#` 总标题包住全文？正文是否由多个一级教学阶段自然展开，并用二级、三级标题继续细分？
35. 图注是否全部使用普通正体文本，没有 `*图：……*`、`_图：……_` 等斜体或会造成文字倾斜、变形的格式？
36. 每个具有可见过程或需要听讲解的知识点是否使用一段最短充分的带原声 MP4，直接从原视频剪辑并完整覆盖入口、关键过程、结果和完整语句；是否没有使用无声二次素材、截断语音或丢失音轨；每段文字描述的动作、对象或变化是否有紧邻媒体？
37. 每个 MP4 是否包含有效同步音轨，使用 Obsidian 可播放的编码，分辨率符合用户要求或 950px 阅读场景，且未无意义放大？是否逐段完整播放并核对了声音、画面、起止点和引用路径？
38. 每个有语音的 MP4 下方是否紧接人工校正后的讲解文字，准确覆盖该片段的人名、产品名、按钮名、专业术语、数字、操作和结果；成品是否没有新增字幕流、烧录字幕或旁挂字幕，也没有为了保留源硬字幕而拼接字幕条或牺牲有效操作区域？
39. 讲解者点名的菜单项、模板、按钮和图标是否配有独立小图或能全部直接读清的紧凑局部图，而不是只剩纯文字列表？
40. 每个 MP4 是否以鼠标实际操作范围作为裁剪主体，逐个确认点击、双击、悬停、拖拽、滚动和输入时的鼠标、操作目标、有效路径，以及鼠标操控区域所属的完整 UI 均完整入镜；菜单链、面板、弹窗、下拉列表、工具栏或工具分组是否没有缺少标题、外框、边缘、当前项或必要关联控件？弱相关的未操作区域是否只是在不破坏完整 UI、定位关系和稳定构图的前提下尽量减少，而没有被当成必须删除的对象？裁剪是否始终使用连续矩形窗口，没有遮罩、黑块、挖空、拼贴或局部删除？
41. 同一连续源画面中每次裁剪中心或倍率变化是否都使用短促、缓入缓出的平滑运镜，裁剪硬切数是否为 0；若存在例外，是否仅属于原片已有切镜、无连续空间关系或不存在安全路径，并已记录逐帧证据和理由？
42. 是否在成品帧率下逐帧检查每个运镜区间，确认曲线连续、单调、无回弹、无越界，起步与停稳无顿挫，所有中间帧都完整保留活动 UI、鼠标目标和必要结果；靠边 UI 是否使用对应边锚定，远距离跨区是否先平滑拉远并稳定交代空间关系后再推近？是否完全没有使用溶解、帧混合、光流补帧、重复帧、运动模糊或变速来制造流畅感？

任一最终栅格图片文件在 100% 原始像素比例下呈现模糊时，不得交付；必须重新取帧、保真增强、调整构图或拆分。若仍无法可靠恢复，该图不得进入成品；如果它不可替代且删除会造成可视描述缺图，不得宣称任务完成，应明确报告阻塞并请求更清晰源素材。不能猜测或生成缺失细节。Obsidian 阅读视图只负责排版和媒体可用性验收，不再作为是否高清化的判断依据。

## 9. 长视频转写与恢复

没有可靠字幕或需要本地识别时，先执行 Skill 自带的 `scripts/resumable_transcribe.py`。每个视频使用独立工作目录。约 300 秒只是目标分段长度，不是固定切点：脚本先检测音轨中的自然停顿，再从目标点前后的候选停顿中选择最近的静音中点作为边界；只有附近没有合适停顿时才按目标时间回退。边界两侧保留少量上下文重叠，并按句段中点归属核心区间，既保护跨边界语义，也避免汇总稿重复。

可靠性要求：

1. 启动后先写入源文件指纹、转写参数、分段计划和状态清单，再加载模型或开始长时间计算。
2. 音频分段、单段 JSON、总体部分转写稿和进度清单全部采用“临时文件写完后原子替换”的方式，禁止直接覆盖有效文件。
3. 每完成一个分段，依次保存单段结果、更新 `progress.json`、重建 `transcript.partial.*`，然后才把该段视为完成。中断时已完成分段必须可独立读取。
4. 使用相同视频、工作目录和参数重新运行时跳过已完成分段；源视频指纹或关键参数发生变化时拒绝误用旧断点，并要求改用新工作目录。
5. 模型加载和每个耗时分段都写周期性心跳。正常事件与错误事件分别进入 `logs/运行.log` 和 `logs/错误.log`，并用同一操作编号关联；日志不得记录音频内容、密钥或其他不必要的隐私信息。
6. 只有全部分段完成后，才把 `transcript.partial.txt/json` 原子改名为正式转写稿。正式文件不存在时必须检查断点与日志，不能仅凭进程退出推断成功。
7. 至少在首段完成后做一次恢复性检查：重新读取进度清单、单段 JSON 和部分转写稿，确认即使此刻中断也能从下一段继续。
8. 最终交付前记录总分段数、已完成分段数、识别模型和工作目录；最终笔记写回源视频目录后再决定是否清理临时音频。
9. 在 `progress.json` 中保留边界来源。`silence` 表示在自然停顿处切分；`time_fallback` 表示附近没有找到合适停顿。出现时间回退时，整理人员必须联合检查相邻分段的末尾与开头，不得把被跨段的同一讲解误写成两个独立知识点。

## 10. FFmpeg 安全执行与防崩门槛

所有抽帧、剪辑、平滑运镜、转码和完整解码检查都必须通过 Skill 自带的 `scripts/safe_ffmpeg.py` 启动。标准调用形式为 `python scripts/safe_ffmpeg.py --ffmpeg <可信的 ffmpeg.exe 绝对路径> -- <FFmpeg 参数>`；只允许 `ffprobe` 做轻量媒体探测。不得从 PATH 自动选择程序，不得直接调用 `ffmpeg.exe`、不得同时运行多个 FFmpeg，也不得用多个代理或后台会话并行渲染不同片段。守卫发现已有 FFmpeg 进程时，本次命令必须保持未启动状态；如果本任务运行期间又出现其他 FFmpeg，立即安全停止本任务，等前一进程正常结束后再运行。

启动前必须同时满足：可用物理内存不少于 3 GiB、可用提交额度不少于 6 GiB。任一条件不满足时暂停启动，先等待现有任务完成或请用户自行关闭非本任务应用；未经用户许可不得结束用户的程序。Windows 下必须在 FFmpeg 第一条指令执行前把挂起创建的子进程加入独立 Job Object，并设置 5 GiB 单进程内核提交上限、6 GiB Job 总提交上限、守卫关闭时终止整个 Job，以及未处理异常不弹出子进程故障对话框；加入或恢复失败时必须终止挂起进程并判为安全失败。运行期间还要逐秒检查 FFmpeg 私有内存和系统余量：私有内存达到 4 GiB 时记录警告，在内核硬上限前主动停止；可用物理内存低于 512 MiB 或可用提交额度低于 2 GiB 时同样停止。任何监控读取失败都必须采用失败关闭策略，终止整个 Job，不能因读不到内存数据而静默禁用上限。停止后必须把当前输出视为失败并删除或隔离不完整候选，再改用更短的时间分段、更简单的滤镜图或稳定段／转场段分别渲染后续跑，不得提高上限、扩大页面文件或关闭 Windows 错误报告来掩盖问题。

输入视频位于 UNC、NAS 或其他网络共享时，先复制到本地稳定工作目录并重新校验文件大小与媒体指纹；转写工作目录、中间音频、抽帧、裁剪和编码也必须全部位于本地稳定目录。成品验证通过后才复制回用户指定目录并重新读取确认。网络盘只作为来源和最终交付位置，不直接承载 FFmpeg、转写或复杂滤镜任务。不得移动、覆盖或删除原始视频。

稳定画面使用普通 `trim/crop/scale`；平滑运镜只应用于短过渡段。每个 `zoompan` 所在的独立视频滤镜链必须自身显式包含 `trim` 并使用 `d=1`，不能借用同一命令中其他输出的 `-t`、`-to`、帧数或另一条滤镜链的 `trim` 作为边界；再把过渡段与稳定段按时间顺序拼接。禁止把 `zoompan` 套在整段视频上，也禁止 `minterpolate`、`tmix`、`tblend`、`xfade`、`fifo`、`afifo`、光流、混帧或其他会缓存、补写或混合大量帧的路径。不得用自动硬件加速规避软件滤镜问题。所有输入明确选择主视频流 `0:v:0`；复杂滤镜从 `[0:v:0]` 取流，音频按需要显式选择 `0:a:0?`，并忽略附加封面、字幕和数据流。输入只允许不带 URI 协议前缀的已验证本地媒体文件；禁止网络协议、媒体清单、concat/HLS/DASH/SDP 输入、协议白黑名单覆盖、外部滤镜脚本，以及 `movie`、`amovie`、`subtitles`、`ass`、`zmq` 等可从滤镜图另行加载文件或网络资源的滤镜。

完整解码 QA 不使用 `-re`、`-readrate` 或类似实时读取参数；快速完整解码负责发现错误，1× 连续目视与听音交给播放器。所有调用加入 `-nostdin` 并等待进程自然退出；需要中止时由守卫先发送正常中断信号，超时后才终止。守卫仅让当前 FFmpeg 子进程不显示 Windows 故障对话框，并保留非零退出码、标准错误和任务失败状态；它不得修改注册表或全局 WER 设置，也不得把没有弹窗误判为成功。

每次任务开始时记录 `ffmpeg -version`、`ffprobe -version` 的首行、可执行文件路径和 SHA-256，并确认两者来自同一发行目录。优先使用可信来源的稳定发行构建；守卫内置的已知重复崩溃构建清单必须作为启动前硬拦截，命中后不得继续承担生产任务。更换 FFmpeg 属于环境变更，先保留旧版本回滚并征得用户同意，不得在视频任务中静默下载或覆盖。任何 FFmpeg 非零退出、守卫触发、输出文件缺失或媒体复核失败都必须写入错误日志，并从最后一个已验证的分段继续，不能把进程结束等同于完成；上层转写或剪辑脚本必须原样保留守卫的 73（已有任务）和 75（资源保护）等退出状态，不能统一折叠成普通退出码 1。
